# 口径变化与旧池回看

用户口头改筛选口径、说“新 JD 还没有”、或要求“盘点之前被卡住的人”时，走这条分支。不要当成一次全新全量 AI 筛选。

## 什么时候走这里

- 同一岗位口径变了，完整新 JD 还没到。
- 用户要回看旧批次里被旧硬条件隔离、不推荐或没入表的人。
- 用户只要增量补新简历，并先对照口述新口径看人。

此时不要自动运行 `inventory`、`preflight`、`run`、`score-only`、`calibrate`、`retry-failures` 或 `finalize`。

## 先定位旧批次，再开新 run

1. 先找这个岗位上次的 `screening-run`：`resumes/`、`job_requirements.md`、`results/`、`work/records/`、邮箱 `--incremental-state`。
2. 新口径单独建本次运行目录，例如 `screening-run-<role>-YYYYMMDD/`。不要覆盖旧 `job_requirements.md`。
3. 邮箱增量继续写入**旧岗位**的 `resumes/`，并复用同一个 `work/email_cursor_<role>.json`。不要另开临时下载目录重扫最近 7/30 天。
4. 本次回看如需单独 `resumes/`，优先硬链接或软链接旧文件；只有跨磁盘不支持链接时才复制。

## 口径怎么记

- 用户口述的改动立即视为最新口径；没被改到的旧字段标“沿用，本次未改”，不要自行补全。
- `job_requirements.md` 写 `JD 状态：临时草稿/待确认`，并写清用户确认记录和未确认项。
- 旧口径整段保留并标日期，不覆盖。新旧冲突时两版都留。
- 不得把下载过滤规则或旧 JD 扩写成一份看起来完整的新 JD。

完整新 JD 仍未确认时，只允许：来源确认、增量下载、manifest、用户指定的预过滤、按口述口径做本地回看。不得全量 AI 筛选，也不得把回看表当成最终交付口径。

## 回看时怎么用旧 AI 结果

旧 `AI 初筛结果`、隔离名单、不入表名单只说明**旧 JD**当时怎么判，不能直接当成新口径的推荐等级。

正确用法：

1. 用旧结果定位“被旧硬条件卡住的人”，例如年限上限、英语、IR、海外税、owner 级别。
2. 用本地文本抽取重读简历（MarkItDown / 本地 PDF 解析 / 本地 OCR）。本用户工作流里，本地仍读不出来时按主 skill 的视觉兜底规则处理，并在结果里标明。
3. 按**最新口述口径**重新判断：现在值得看 / 仍不必看 / 信息不足需复核。
4. 输出里同时保留：旧结果、旧结果卡住的原因、新口径为什么改判。

不要为了回看把整批旧简历重新丢进智谱。只有用户明确要求按已确认新 JD 重筛时，才另开 `work/` 跑模型；不要复用旧岗位的 `work/` 缓存。

## 回看交付物

写进本次 `results/`，至少包含：

- 现在值得看的人，以及对照新口径的理由。
- 仍不必看的典型反例，以及被哪条新/旧条件排除。
- 增量新下载、尚未按新口径判断的文件数。
- 口径仍是草稿、完整 JD 未到的标记。

入飞书表前，先让用户确认这份回看名单；入表规则见 `feishu-delivery.md`。
